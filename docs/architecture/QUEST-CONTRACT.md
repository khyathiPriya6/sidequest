## Domain model

`Quest` is an authored challenge with a single immutable creator and a controlled lifecycle. Participation, completion, XP awards, proof, and social features are outside SQ-008 and belong to later scopes.

| Field | Type / constraint | Draft behavior |
|---|---|---|
| `id` | UUID, generated by the server, primary key | Always present |
| `creatorId` | Same identifier type as `users.id`; required foreign key | Derived from the authenticated principal, never accepted from the request |
| `title` | String, 3–120 Unicode code points after trimming; required | Required |
| `description` | String, 10–3000 Unicode code points after trimming | May be null until publish |
| `category` | `ADVENTURE`, `CREATIVITY`, `FITNESS`, `LEARNING`, `FOOD`, or `SOCIAL` | May be absent until publish |
| `difficulty` | `EASY`, `MEDIUM`, or `HARD` | May be absent until publish |
| `rewardXp` | Integer from 1 through 1000 | May be absent until publish |
| `status` | `DRAFT`, `PUBLISHED`, or `ARCHIVED` | Server-managed; new quests start as `DRAFT` |
| `createdAt` | UTC instant; immutable | Set by the server |
| `updatedAt` | UTC instant | Set by the server on each actual mutation |
| `publishedAt` | Nullable UTC instant | Set on first publish and retained after archive |
| `archivedAt` | Nullable UTC instant | Set when archived |
| persistence version | Monotonically increasing integer, internal | Used to produce an ETag; not client-editable |

The database uses a restrictive foreign key from `quests.creator_id` to `users.id`, non-null constraints for `id`, `creator_id`, `title`, `status`, and timestamps, and checks for enum values and any non-null `reward_xp`. Fields that can be omitted from a draft remain nullable until publication. Published quests must satisfy every required field constraint.

The identity schema defines `users.id` as UUID; Quest persistence uses that key without creating a second identity model. Quest IDs are also server-generated UUIDs.

### Rationale

| Decision | Reason |
|---|---|
| Server-generated UUID for quests | Avoids exposing database sequence behavior and gives web/API clients a stable opaque identifier. The creator key still follows the users schema. |
| Immutable `creatorId`, derived from the principal | Prevents request-body spoofing and makes ownership checks consistent for every operation. |
| Title required on draft; other publish fields may be null | Lets a creator save and find a meaningful partial draft without treating an incomplete draft as discoverable. |
| Bounded title, description, and XP | Rejects empty/oversized content and implausible rewards at the API boundary; limits are product guardrails, not a measure of quest quality. |
| Fixed category and difficulty enums | Keeps filtering and client labels consistent across web and future mobile clients, rather than accumulating spelling variants. |
| UTC timestamps and separate lifecycle timestamps | Makes ordering independent of client timezone and preserves when publication/archive occurred for later history. |
| Archive instead of deletion; no reopen | Preserves ownership and future participation references while keeping the MVP state machine simple and auditable. |
| Internal version exposed as ETag | Allows optimistic concurrency without making clients edit database version fields; stale changes fail instead of overwriting newer edits. |

### Draft and publish validation

- Draft creation requires a non-blank title of 3–120 Unicode code points. Description, category, difficulty, and reward may be omitted while drafting.
- Any optional field supplied on create or patch must still be valid: description is 10–3000 Unicode code points; category and difficulty must be one of the enumerated values; reward is an integer from 1–1000.
- On create, omitted or `null` optional fields are unset. On `PATCH`, an omitted field is unchanged and an explicit `null` clears an optional field while the quest is a draft; `title` cannot be cleared. A cleared field must be provided again before publication.
- Publish requires a valid title, description, category, difficulty, and reward. An invalid publish returns field-level validation errors and leaves the quest in `DRAFT`.
- Trim surrounding whitespace before checking string lengths and storing values. Reject invalid enum values and non-integer/out-of-range reward values; do not silently coerce them.
- `id`, `creatorId`, `status`, and lifecycle/audit timestamps are server-managed and cannot be changed through the draft update request.
- Published content is immutable in the MVP. In particular, do not change the XP reward or material completion requirements after participants exist, consistent with the PRD.

The bounds and six-category taxonomy above are requester-confirmed proposals. The design documents suggest these categories and difficulty levels but do not constitute owner approval of the visual design.

## Lifecycle and ownership

Allowed transitions:

```text
DRAFT ──publish──> PUBLISHED ──archive──> ARCHIVED
  └────────────────archive─────────────> ARCHIVED
```

- Creation always produces a draft. Publishing is allowed only after publish validation succeeds.
- Only the creator may read a private quest, edit a draft, publish it, or archive it.
- Published quests are visible in public list and detail endpoints. Drafts and archived quests never appear in public discovery or public detail.
- A creator may read their own draft or archived quest through an authenticated owner route. Archived quests are immutable.
- Publishing an archived quest, editing a published or archived quest, or any other unsupported transition returns `409 Conflict`.
- Repeating publish for an already-published quest or archive for an already-archived quest is idempotent: return `200 OK` with the unchanged current representation and do not change timestamps or version.
- Permanent deletion and reopening are not supported. Archive preserves the quest record and any future participation history.
- For a missing quest or a private quest requested by a non-owner, return `404 Not Found` so the API does not reveal whether the private resource exists. Missing authentication on a protected operation returns `401 Unauthorized`.
- For `GET /api/v1/quests/{id}`, unauthenticated callers and authenticated non-owners both receive the same `404` for a draft or archived quest; the route remains public for published quests. `401` applies to protected writes and owner-only collection routes when no principal is present.
- Ownership is enforced on the server from the authenticated principal, not from client-supplied IDs or UI state.

## API conventions

All routes use `/api/v1`, JSON uses camelCase, and timestamps are ISO 8601 UTC strings ending in `Z`, following [API conventions](./API-CONVENTIONS.md). Protected routes require an authenticated principal. The authentication mechanism and token/session storage are intentionally not selected here; they require the E03 identity work and its security ADR.

### Endpoints

| Method and path | Access | Contract |
|---|---|---|
| `GET /api/v1/quests` | Public | Published quests only; optional `q`, `category`, and `difficulty` filters; paginated |
| `GET /api/v1/quests/{id}` | Public for published; owner-only otherwise | Returns a published quest publicly; creator may also read their own draft or archived quest |
| `GET /api/v1/me/quests` | Authenticated | Lists only the caller's quests, including drafts and archived quests; optional `status` filter; participation views are out of scope |
| `POST /api/v1/quests` | Authenticated | Creates a draft; returns `201 Created` and a `Location` header |
| `PATCH /api/v1/quests/{id}` | Authenticated owner | Updates draft fields only; requires `If-Match`; returns `200 OK` |
| `POST /api/v1/quests/{id}/publish` | Authenticated owner | Validates and publishes a draft; returns `200 OK` |
| `POST /api/v1/quests/{id}/archive` | Authenticated owner | Archives a draft or published quest; returns `200 OK` |

The create request accepts `title` and any optional draft fields from the domain table. It does not accept `id`, `creatorId`, `status`, timestamps, or version. `PATCH` accepts only fields to change and applies the same per-field validation as draft creation. Publish and archive requests have no body.

```http
POST /api/v1/quests
Content-Type: application/json

{"title":"Explore a new walking route"}
```

The public `q` filter is a case-insensitive substring match against title and description. `category` and `difficulty` accept the exact enum values. Public results are ordered by `createdAt` descending and then `id` descending for deterministic pagination.

### Pagination

Use zero-based `page` (default `0`) and `size` (default `20`, maximum `100`). Invalid or out-of-range pagination inputs return `400 Bad Request`; do not silently clamp them.
Page/size metadata lets clients render predictable navigation, while a maximum size bounds database and response work. A deterministic tie-breaker keeps ordering stable when multiple quests share a creation timestamp.

```json
{
  "content": [],
  "page": 0,
  "size": 20,
  "totalElements": 0,
  "totalPages": 0,
  "hasNext": false,
  "hasPrevious": false
}
```

### Success representation

The same Quest representation is used by create, read, update, and lifecycle responses. Nullable draft fields and timestamps are explicit `null` values.

```http

Location: /api/v1/quests/018f47d1-7c61-7e00-9a7c-000000000001
ETag: "1"
Content-Type: application/json
```

```json
{

  "creatorId": "018f47d1-7c61-7e00-9a7c-000000000002",
  "title": "Explore a new walking route",
  "description": null,
```

### Error convention

Use RFC 9457 Problem Details (`application/problem+json`) for errors. Validation problems include an `errors` extension containing field, code, and message. Do not include stack traces or private quest data. The standard problem fields give every client the same status/title/detail shape; the field-error extension preserves actionable form feedback without inventing a separate response envelope.

```json
{
  "type": "about:blank",
  "title": "Request validation failed",
  "status": 422,
  "detail": "The quest cannot be published until its required fields are valid.",
  "instance": "/api/v1/quests/018f47d1-7c61-7e00-9a7c-000000000001/publish",
  "errors": [
    {
      "field": "description",
      "code": "required",
      "message": "Description is required when publishing."
    },
    {
      "field": "category",
      "code": "required",
      "message": "Category is required when publishing."
    },
    {
      "field": "difficulty",
      "code": "required",
      "message": "Difficulty is required when publishing."
    },
    {
      "field": "rewardXp",
      "code": "required",
      "message": "XP reward is required when publishing."
    }
  ]
}
```

Use `400` for malformed requests/query parameters, `401` for missing authentication on protected operations, `404` for missing or non-owned private quests, `409` for unsupported lifecycle transitions, `412` for stale `If-Match`, `422` for semantically invalid quest fields or publication, and `428` when a required `If-Match` is absent, consistent with [API conventions](./API-CONVENTIONS.md).

### Private-resource example

A non-owner requesting a draft receives the same response as a nonexistent quest; the response does not disclose its title, status, or owner.

```http
GET /api/v1/quests/018f47d1-7c61-7e00-9a7c-000000000001
HTTP/1.1 404 Not Found
Content-Type: application/problem+json
```

```json
{
  "type": "about:blank",
  "title": "Resource not found",
  "status": 404,
  "detail": "The requested resource was not found.",
  "instance": "/api/v1/quests/018f47d1-7c61-7e00-9a7c-000000000001"
}
```

### Stale-update example

The client sends the ETag it read. If another update has advanced the resource to ETag `"3"`, the stale update is rejected without applying the patch.

```http
PATCH /api/v1/quests/018f47d1-7c61-7e00-9a7c-000000000001
If-Match: "2"
Content-Type: application/json

{"title":"A different title"}
```

```http
HTTP/1.1 412 Precondition Failed
Content-Type: application/problem+json
ETag: "3"
```

```json
{
  "type": "about:blank",
  "title": "Precondition failed",
  "status": 412,
  "detail": "The quest changed after it was read. Fetch the latest version before retrying.",
  "instance": "/api/v1/quests/018f47d1-7c61-7e00-9a7c-000000000001"
}
```

## Concurrency and retry behavior

- Return a strong ETag for every Quest representation, derived from the persistence version.
- Require the exact current ETag in `If-Match` on `PATCH`, publish, and archive.
- If the resource changed after the caller read it, return `412 Precondition Failed` with Problem Details and make no mutation.
- If `If-Match` is absent, return `428 Precondition Required`.
- `If-Match` remains required on publish/archive requests. For an already-completed action, return the unchanged current representation before comparing its supplied ETag; this allows a retry after a successful transition while still requiring conditional requests.
- Increment the version and update `updatedAt` only on a real content or lifecycle change. A repeated idempotent action does neither.

## Authentication and users dependency

The E03 identity migration defines the `users` table and UUID primary key. Authentication/security implementation is not present on the current `main` branch, so protected Quest APIs cannot ship until the Spring Security and authentication API work is integrated and verified.

Quest implementation depends on E03 (#3) providing:

1. A `users` table and stable primary-key type; provided by the E03 persistence migration, with `quests.creator_id` referencing `users.id`.
2. Registration/login/session behavior and an authentication ADR; the contract is in ADR 0002, while runtime security/authentication must be integrated into `main`.
3. A server-side principal exposing the authenticated user ID for creator assignment and ownership checks; required before protected API implementation.
4. Protected-route authorization and tests demonstrating unauthenticated `401`, non-owner private-resource `404`, and creator-only mutation.
5. A profile display-name field and exposure rules before public Quest responses can show creator names.

SQ-008 can define the Quest contract without E03 implementation, as its issue says. However, protected Quest writes and owner-only access cannot be released before identity and authorization are available. This reconciles the E02/M1 design placement with the PRD's rule that protected business endpoints wait for identity.

## SQ-008 learning notes

- **What this phase defines:** A server-owned Quest resource and its allowed states, request/response shapes, validation, visibility, pagination, and conditional mutation behavior. No runtime code or schema is implemented here.
- **Why these choices:** Drafts support incomplete creation without exposing incomplete quests. A small explicit state machine makes publication and archival predictable. Principal-derived ownership and concealed `404` responses protect private resources. UTC instants avoid timezone-dependent ordering. ETags prevent lost updates without putting persistence versions in request bodies.
- **Concepts to understand:** A DTO is the API's stable representation, separate from a database entity. A state machine limits valid transitions. Optimistic concurrency detects conflicts rather than locking users out. HTTP Problem Details standardizes error metadata, while an extension carries field-specific validation feedback.

3. Why might an API return the same `404` for a missing resource and a private resource owned by someone else?
